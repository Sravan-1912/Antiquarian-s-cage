# Antiquarian's Cage — System Architecture

Status: **Design baseline (Phase 0)**. This document is the reference for every later phase.
Anything described here as "planned" is not implemented until the phase that delivers it is
marked complete in `documentation/04-roadmap.md`.

## 1. Requirements analysis (condensed)

The platform has three trust domains and five functional pillars.

| Pillar | Core capability | Phase |
|---|---|---|
| Identity & administration | Admin auth, MFA, RBAC, employees, JML workflows | 1, 5 |
| Endpoint management | Agent, enrollment, inventory, heartbeat, lifecycle | 2 |
| Security posture | Policies, deployment jobs, compliance engine | 3 |
| Remote administration | Allowlisted commands, consented assistance sessions | 4 |
| Security operations | Alerts, tamper-evident audit, notifications, reports | 6 (audit core in 1) |

Key non-functional requirements extracted from the brief:

* Backend is the **only** authorization authority. The UI hides things for usability, never for security.
* No metric is ever fabricated. Empty databases show zeros / empty states, not demo values.
* Endpoints, the agent and the network are assumed hostile. Agent-reported data is *evidence*, not truth.
* Single organization at launch, but every tenant-scoped table carries `organization_id` from day one.
* Every privileged action produces an audit event in the same DB transaction as the action.

Two separate listeners exist on purpose: the admin console uses browser sessions; the
agent channel uses client certificates. A stolen admin cookie cannot impersonate a device,
and a stolen device certificate cannot reach admin endpoints (different router, different
auth dependency, different Nginx server block).

## 3. Communication contracts

### 3.1 Frontend ↔ backend
* REST JSON under `/api/v1`. OpenAPI generated by FastAPI at `/api/docs` (disabled in production unless `EXPOSE_API_DOCS=true`).
* **Session model:** opaque random session ID (256-bit) in an `HttpOnly; Secure; SameSite=Strict` cookie. Server stores only the SHA-256 of the ID in `user_sessions`. This makes revocation immediate and avoids JWT-in-localStorage XSS exposure.
* **CSRF:** double-submit token. A non-HttpOnly `cage_csrf` cookie is issued at login; every state-changing request must echo it in `X-CSRF-Token`. Combined with `SameSite=Strict`.
* **WebSocket** `/ws/events`: authenticated by the same session cookie at handshake + Origin check; pushes notifications and dashboard invalidation hints. The client re-fetches via REST — WS never carries authorization-sensitive data that REST would not.

### 3.2 Agent ↔ backend (Phase 2)
1. Admin creates an **enrollment token** (single use, 15-minute TTL by default, optional target employee). Only its SHA-256 is stored.
2. Agent generates an Ed25519/ECDSA P-256 keypair locally (private key protected with DPAPI machine scope) and sends a CSR + token to `/agent/v1/enroll` (the only agent endpoint that does not require mTLS; it is rate-limited and token-gated).
3. Backend validates token, signs a **device certificate** (CN = device UUID, 90-day lifetime) with the internal device CA, records fingerprint in `device_certificates`, burns the token.
4. All further calls use mTLS. Nginx verifies the chain; FastAPI re-checks the fingerprint against `device_certificates` (status `active`) on every request so revocation is immediate without CRL distribution.
5. Heartbeat every `HEARTBEAT_INTERVAL_SECONDS` (default 60). A device is **online** iff `now - last_authenticated_heartbeat < OFFLINE_THRESHOLD_SECONDS` (default 180).
6. Jobs are pulled (agent polls `/agent/v1/jobs`), never pushed, so endpoints need no inbound ports.

### 3.3 Command envelope (Phase 3/4)
```json
{
  "job_id": "uuid", "device_id": "uuid", "command": "policy.firewall.apply",
  "schema_version": 1, "policy_version": 7, "parameters": { ... },
  "issued_at": "...", "expires_at": "...", "nonce": "128-bit random",
  "key_id": "cmd-2026-01", "signature": "ed25519(base64)"
}
```
Agent rejects if: unknown `command`; parameters fail the local JSON schema; `device_id` ≠ own identity;
expired; nonce already seen (persisted ring of nonces until expiry); signature invalid for a pinned key ID;
`policy_version` older than the last applied version. The command signing key is **separate** from the
TLS CA and from the audit-chain key.

## 4. Backend module layout

```
backend/app/
  core/        config, database, logging, security headers, rate limiting
  security/    passwords (Argon2id), sessions, CSRF, TOTP, permissions, crypto (AES-GCM)
  models/      SQLAlchemy ORM (one module per bounded context)
  schemas/     Pydantic request/response models
  services/    business logic; the only layer that writes audit events
  api/         routers; thin — validation + dependency-injected authz + service calls
  workers/     Celery app and tasks
  integrations/ email (SMTP), future OIDC/SAML adapters
```

Authorization is expressed as permission strings (`employees:write`, `devices:suspend`, …).
Routers declare `Depends(require_permission("employees:write"))`. Roles are bundles of permissions
stored in the DB (`role_permissions`), seeded by migration, so roles can be customised later
without code changes.

## 5. Frontend module layout

Feature modules under `src/modules/<domain>` own their pages, API hooks and components.
Shared primitives (shadcn/ui-style components) live in `src/components/ui`. The API client
(`src/services/api.ts`) centralises CSRF header injection, error normalisation and 401 handling.
The user's effective permission list is returned by `/auth/me`; the UI uses it only to hide
controls the backend would reject anyway.

## 6. Multi-tenancy readiness
* `organizations` table exists; every tenant-scoped row has a non-null `organization_id` FK.
* Services always filter by `current_user.organization_id`; there is no "global" query path.
* Postgres Row-Level Security policies are documented as a Phase 7 hardening item.
